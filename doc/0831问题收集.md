# 0831问题收集

## 问题一：自然语言路线为什么要删除疑问句开头？

### 问题具体内容

当前拆解文档写道：

> 用规则删除疑问句开头，例如 `What is`、`Does`、`Describe`；并保留清理后的整句作为自然语言路线输入。

需要确认：自然语言路线本来用于保留原始问题语境，删除 `What is`、`Does` 等疑问句元素是否真的有助于 PubMed 检索？还是会损失语义信息？

### 当前代码位置

- [query.py](../plugins/medlit-cli/medlit/pubmed/query.py) 第73行：`clean_natural_query`。
- 第73—89行：只清理句首疑问框架，不对整句做结构化拆分。
- 第201行：`QueryBuilder`。
- 第239—242行：清理后的文本进入 `Q0_cleaned_natural`，该路线不加字段标签，交给PubMed自动术语映射。
- 第68行：`_looks_like_question` 用于判断输入是否像问题。

### 当前实际行为

例如：

```text
Does Plozasiran reduce triglyceride levels?
→ Plozasiran reduce triglyceride levels

What is the mechanism of action of Nipocalimab?
→ mechanism of action of Nipocalimab
```

当前规则只删除句首的疑问结构，不删除后续医学词语，也不把自然语言路线改造成PICO检索式。

### 当前判断

删除疑问框架的理由是：`Does`、`What is`、`Describe` 通常不是医学概念，保留它们可能增加无效词。但这只是合理假设，不应直接当作已验证的召回率改进。

还存在另一种可能：PubMed本身会忽略或自动处理部分常见词，因此清理前后的效果可能没有实质差异。若清理规则过宽，也可能误删具有医学意义的句首表达。

## 后续实验

### E1：清理前后对照

固定以下条件：

- 同一批医学问题；
- 同一份PICO JSON；
- 同一PubMed时间条件；
- 同一 `retmax`；
- 只替换Q0文本，其余结构化路线、锚点路线和RRF设置不变。

比较两组：

```text
A组：原始完整问题
B组：clean_natural_query处理后的问题
```

记录：

1. PubMed返回的 `querytranslation` 是否变化；
2. 总命中数和前100 PMID是否变化；
3. 仅由A组或B组找回的标准答案论文；
4. 单独使用Q0时的 Recall@10、Recall@100、Hit@10、MAP@10；
5. 加入其他路线后，最终RRF排名是否变化。

### E2：规则边界测试

至少覆盖：

- `Does [药物] reduce [结局]?`
- `What is the mechanism of [药物]?`
- `Describe [疾病或基因]`
- 非英语问题；
- 句首疑问词本身可能是医学术语的情况。

重点检查：清理后是否仍保留药物、疾病、干预和结局；是否出现空查询或关键短语被截断。

### 判定标准

- 如果B组在多数问题上提高或保持标准答案召回，且没有稳定的关键实体损失，可以保留当前规则。
- 如果A/B差异很小，应将其定性为低优先级规范化，而不是核心检索改进。
- 如果B组漏掉A组能够找到的关键标准答案，应缩小清理规则，或保留原始问题作为额外自然语言路线。

### 记录要求

该问题属于“自然语言检索式规范化”的待验证事项，不得与PICO拆解、结构化概念路线或RRF融合的效果混在同一结论中。实验必须使用全新 `state.json`，并保存原始问题、清理后文本、完整 `query_ladder` 和每路检索结果。

## 问题二：以 Codex 直接承担 S10 query/lane 构建，并保证路线具有实际区分

### 问题与决定

当前 `plan-terms` 由 `plugins/medlit-cli/medlit/pubmed/query.py:92-198` 的 `TermPlanner` 执行，依赖停用词、泛词、短语边界和少量医学特例等硬编码启发式规则；随后由同文件 `QueryBuilder`（约 `:201` 起）在 S10 拼装 `query_ladder`。命令入口位于 `plugins/medlit-cli/medlit/cli.py:126-190`。

后续改造并非只让 Codex 产生新的 `term_plan` 后继续交给旧 `QueryBuilder`，而是取消 S07 至 S10 之间以 `term_plan` 为中间产物的默认硬编码构建链，由当前运行 Skill 的 Codex 根据原始问题、用户约束及 PubMed 查询规则，直接承担 S10 的多条 query/lane 构建职责。Python 脚本不在内部再次调用 Codex。

### 当前 S10 多 lane 的区分度问题

当前设计最多产生五条 lane，但不是每次固定生成五条；显式过滤和 comparator 不存在时，`Q2_explicit_filters`、`Q3_with_comparator` 不会出现。

从构造关系看，除 `Q0_cleaned_natural` 外，其余路线都来自同一份 `title_abstract_terms`：

| lane | 与其他路线的关系 | 当前判断 |
|---|---|---|
| `Q0_cleaned_natural` | 保留清理后的自然语言且不加字段标签，交给 PubMed ATM | 与结构化路线区别最明显 |
| `Q1_structured_recall` | 同概念内 OR、概念间 AND，是结构化路线的共同基础 | 结构化主路线 |
| `Q1b_entity_anchor` | 从 Q1 的相同词集中选择较长词组并增加 AND | 通常是 Q1 的更严格版本，不是独立概念来源 |
| `Q2_explicit_filters` | 在 Q1 后追加用户明确指定的人群或语言过滤 | 本质上是 Q1 的受限子集 |
| `Q3_with_comparator` | 在 Q1 后再 AND comparator | 本质上也是 Q1 的受限子集 |

因此，当前真正明显互补的是自然语言路线与结构化路线；其余结构化 lane 虽然可能改变结果和排序，但高度相关，更像围绕 Q1 的逐级收紧，而不是四种独立检索策略。这会带来一个需要后续验证的问题：同一论文若同时出现在多个相关性很高的结构化 lane 中，会在 RRF 中获得多次加分。RRF本身没有错误，但它会把这些 lane 当作不同排名信号，可能放大重复信号。

当前阶段只记录这一风险，不据此判断 RRF 或现有 lane 的实际检索效果。lane 的 PMID 重合率、排名相关性和对最终指标的贡献需要在后续效果评估阶段单独检查。

### 本阶段范围

1. 补齐 `plugins/medlit-cli/skills/medlit-cli/SKILL.md` 的 instruction，明确 Codex 生成检索式时的输入、输出格式、lane 要求、字段标签和禁止行为；每条 lane 还应声明检索目的，避免只做无意义的字符串微调。
2. 规划并新增一个确定性的 query 语法检查脚本，只检查检索式是否能安全进入后续执行流程。
3. 旧 `TermPlanner`、`QueryBuilder` 和原 `plan-terms` 相关脚本全部保留，不删除，作为兼容入口、回退能力及以后对照实验的基线。
4. 本阶段不判断 Codex query 的实际检索效果，不运行 BioASQ 召回率、MAP 或相关性对照；效果评估属于后续独立阶段。
5. 当前仅记录工作内容，暂不修改 Skill、CLI、状态机或检索代码。

### 语法检查脚本的预定边界

脚本只负责可确定判断的内容，包括：

- query 是否为空，lane ID 是否存在且唯一；
- 是否出现完全相同的重复 query；
- 圆括号和双引号是否配对；
- `AND`、`OR`、`NOT` 是否处于合法位置；
- PubMed 字段标签是否属于允许集合；
- 是否含控制字符、明显截断或无法解析的结构；
- lane/query JSON 是否符合约定字段和类型；
- 输出结构化的 `valid`、`errors` 和 `warnings`，供 Codex 修订。

语法检查只能识别完全重复的 query，不能判断两条不同字符串是否在语义上高度相似。命中数量、PMID重合率、PubMed query translation、召回率、相关性、排序质量和医学正确性不属于该语法检查脚本的职责。

## 问题三：S07 的 MeSH 候选生成过于简化

### 问题归属

该问题主要属于 S07 `plan-terms`，并影响 S08 `validate-mesh` 的输入质量。

### 具体问题

`TermPlanner` 先从 PICO 字段提取普通题名/摘要词，再通过标题式大小写生成 `mesh_terms`。这不是基于 MeSH 词表的术语构建，字段实际含义更接近 `mesh_candidates`。

对应代码：

- `plugins/medlit-cli/medlit/pubmed/query.py:95-114`：生成概念及 `mesh_terms`；
- `plugins/medlit-cli/medlit/pubmed/query.py:107`：产生普通 `title_abstract_terms`；
- `plugins/medlit-cli/medlit/pubmed/query.py:111`：将普通词改成标题式大小写后作为候选；
- `plugins/medlit-cli/medlit/pubmed/mesh.py:19-24`：S08 遍历上述候选；
- `plugins/medlit-cli/medlit/pubmed/mesh.py:46-62`：通过 NCBI ESearch/ESummary 查找 MeSH 记录；
- `plugins/medlit-cli/medlit/pubmed/mesh.py:64-88`：按首选词或入口词的字面一致性判定。

### 当前风险判断

E-utilities只能返回与查询字符串匹配的 MeSH 记录，不能保证该记录就是问题语境中真正对应的医学概念。当前实现也没有检查 Scope Note、记录类型、MeSH Unique ID、树分类或多记录歧义。因此，S08目前只能证明候选字符串在某条 MeSH 记录中是首选词或入口词，不能证明医学语义和检索策略正确。

### 后续处理边界

- 在 Codex 直接构建 query 的改造中，不得把模型生成的词未经核验直接添加 `[MeSH Terms]`；
- MeSH继续保持实验路径，不作为默认检索的强制阶段；
- 若以后改进，应至少记录 MeSH Unique ID、记录类型、首选词、入口词、Scope Note 和树分类，并对歧义映射采取拒绝或人工确认；
- 是否值得投入该改造，应在默认 query 构建改造完成后，根据剩余问题再决定。
